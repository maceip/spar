What Spar tests

Tool abuse

Tricking an AI into emailing another user's private invoice or issuing an unauthorized refund.

Shared memory poisoning

Planting hidden instructions in memory so a different user's later chat leaks private data.

Hidden prompt injections

Sneaking commands inside shared documents, images, non-English messages, or connected tools.

False completions

Catching an AI that claims it deleted or updated a record when no tool ever ran.

How it works

01 / AIM

Map the surface

Reads your codebase—or probes your live AI—to map what tools, data, and permissions it can reach.

02 / PROVE

Attack with proof

Runs repeated trials and only reports an issue when hard evidence confirms it and an independent replay reproduces it.

03 / HAND OFF

Report & re-test

Outputs a report, a failing test suite, and remediation context, then re-attacks after a patch lands with spar replay.

Run against your own AI

spar run --target http://localhost:8000 --repo .   # with source code
spar run --target http://localhost:8000          # black-box (no source code)
spar replay                                      # re-attack after a patch lands

Safety by default

Spar only contacts localhost and hosts explicitly allowlisted in spar.yaml, keeps state-changing actions disabled unless you opt in, and never writes account tokens or API keys into reports or generated tests.
